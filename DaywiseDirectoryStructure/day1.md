## What each thing signifies

- **`migrations/`** — schema-as-code. One file so far, `001_init.sql`, hand-written (no ORM migration tool). Applied once manually via Supabase Studio's SQL editor, then formalized via `scripts/migrate.ts` so it's reproducible from a clean DB, not just something that happened once in a GUI.
- **`scripts/migrate.ts`** — reads every `.sql` file in `migrations/`, sorted by filename, and runs it against `DATABASE_URL`. Confirmed idempotent: re-running it against tables that already existed (created via Studio) produced only `NOTICE: already exists, skipping` — no errors, no duplication.
- **`supabase/`** — local Postgres + pgvector, running in Docker via the Supabase CLI. Two config files exist side by side on purpose (see table above); the currently *running* containers were started against the ports in `config.toml_generatedbysupabaseinit` (54321–54324), not `config.toml`'s ports — a known mismatch, left alone intentionally. A future `supabase stop && supabase start` will follow `config.toml` (the old-ports version) and could come up on different ports than `.env` currently expects.
- **`app/`, `.vscode/`, `eslint.config.mjs`, `next.config.ts`, `postcss.config.mjs`, `tsconfig.json`, `public/`, `pnpm-workspace.yaml`** — all default output of `pnpm create next-app` (Next.js 16, React 19.2). Not yet touched by hand.
- **`.env` / `.env.example`** — `.env` holds the real local `DATABASE_URL` (points at local Supabase Postgres) and is gitignored; `.env.example` is the checked-in template with the shape but no real secrets.
- **`CLAUDE.md`** vs **`PLAN.md`** — `CLAUDE.md` is the short, auto-loaded quick-reference (stack, run commands, non-obvious gotchas) any Claude Code session reads at start. `PLAN.md` is the full roadmap and progress log — too long/detailed to belong in `CLAUDE.md`, but the place a fresh session should check for "what's actually been done."
